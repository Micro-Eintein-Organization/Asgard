## Functional differences and review findings

1. **Account state must remain API-backed.** Their new `frontend/src/lib/learning-state.ts` uses browser-wide `asgard.current-learning-topic` and `asgard.topic-statuses` keys. It is not scoped by account. Current `frontend/src/features/core/data.ts` scopes queries to the account and checks the current account before mutation. Copying their state module into active progress flows would introduce a second authority and cross-account browser-state exposure.
2. **Recommendation preparation is not equivalent.** Their Discovery See suggestions passes a navigation-state draft into fixed fixture recommendations. Current Discovery saves versioned answers and invokes the recommendation flow; current results preserve provider failures, previous eligible successes, outdated context and retry feedback.
3. **Set as Career is navigation only in their code.** In their `frontend/src/features/recommendations/page.tsx:157`, the action navigates to a roadmap without persisting focus. Their roadmap's Set as current roadmap button remains disabled. This label cannot establish a new save contract. Current results also deliberately browse a selected roadmap before an explicit focus save.
4. **Retake restores the draft.** Their results link passes `location.state` back to Discovery, including its final step and answers. Their own component test explicitly asserts this restoration. Treat this as an intentional behavior in their source that differs from a fresh retake; do not silently replace current account retake handling.
5. **Blue contrast needs adjustment.** White on their `#3F8AC8` selection/hover fill computes to approximately 3.6967:1. Normal selected-card text and shared primary-button hover text need 4.5:1. Their status-count contrast tests do not cover this blue/white pair.
6. **Selected Results typography changes on selection.** Their stylesheet sets all selected card category/headings/paragraphs/list items to 1rem and font-weight 600. Selecting a card therefore changes content hierarchy and potentially wrapping/card height, not merely color. Verify whether this is intended in the visual reference.
7. **Search documentation and CSS disagree.** Their UI guide says native and app clear controls are available independently, but their final stylesheet hides WebKit search cancel/decoration and MS clear controls for `#career-search`. The JSX supplies one app clear button and Escape handling. Their component test title mentions native clearing but exercises the app button and Escape, which cannot prove a native pseudo-control is visible.
8. **PreviewDataState reset fallback has a static logic issue.** Their `frontend/src/components/preview-states.tsx:30` uses `action ?? (state === "empty" && emptyAction) ?? ...`. For error/loading without an explicit action, the middle value is false, so the onReset fallback is skipped. Current callers may not exercise it; adapt this helper only with the actual intended callers in mind.
9. **Their tests target the older screen tree.** The new learning-flow tests import feature pages and construct their own memory router, while current screen mapping loads DashboardScreen, RoleCatalog and DiscoveryWizard. Wholesale copying tests would either miss current routes, reference removed questions/state modules or assert obsolete fixture behavior. Browser presentation tests inject a synthetic auth session and mock Profile, so they do not certify current authenticated backend integration.
10. **Configuration and routing must be retained deliberately.** Their final Vite file does not contain the current hosted-environment validation. Their router defaults /roadmaps to Frontend rather than resolving saved focus, lacks current /catalog and /settings aliases and /profile-setup, and uses separate account settings. These are older-baseline differences, not changes authored by their eight commits.
